# v0.2.1 Reliability — Technical Design

- **Status:** awaiting approval. No code has been changed yet.
- **Roadmap:** [ROADMAP.md › v0.2.1](../ROADMAP.md#v021--reliability-approved)
- **Evidence:** [AUDIT.md](../AUDIT.md). Risk IDs (R1, R2, …) refer to its §3.

## Goal

Make the existing local workflow safe and correct, so that the later features (new diagram types, search, incremental and impact analysis) are built on data that can be trusted. This release adds **no new user-facing features**.

## Work items

Each item below is one commit with its own tests, done in the order listed.

### 1. Keep every path inside `.omm/` (R1, S1)

**Problem:** `classDir` and `nodeDir` in `src/lib/store.ts` join paths given by the user with no checks. In the audit, `omm delete ../src` deleted the project's `src/` folder.

**Design:**

- Add one helper to `store.ts`: `resolveElementDir(elementPath: string, cwd?)`.
  - It splits the path on `/`.
  - It rejects any segment that is empty, starts with `.` (which covers `.` and `..`), or contains `\`, `:` or a NUL character.
  - It also rejects absolute paths.
  - After joining, it checks that the result is inside `.omm/` (the same check as `resolvePullDestination`).
- `classDir` and `nodeDir` call this helper. Every public store function goes through one of the two, so this one change protects all of them: `read`, `write`, `delete`, `show`, `diff`, `refs`, `validate`, and the API.
- Rejected paths throw an `Error` with the message `invalid element path '<p>'`. The CLI's existing top-level `catch` prints the message and exits with code 1.
- The API returns HTTP 400 for rejected paths.
- `deleteClass` additionally refuses to delete the `.omm/` folder itself.

**Compatibility:** element names the skill produces are kebab-case, so valid names are unaffected. Only names that start with a dot change behaviour, and `listClasses` already hides those.

**Tests:** new `src/__tests__/paths.test.ts`:

- `write`, `read` and `delete` reject `..`, `../x`, `a/../../x`, `/abs`, `C:\x`, `.hidden` and an empty path.
- After `delete ../src` is rejected, a file in the sibling `src/` folder still exists.
- Nested paths that are valid still work.

### 2. A safe, local, offline viewer (R2, R3, S1)

**Problems:**

- The server listens on `::` (every network interface).
- It sends `Access-Control-Allow-Origin: *`.
- Markdown goes into `innerHTML` without sanitising.
- `marked` is loaded from a CDN with no version pin.
- The viewer posts all its data to *any* page that frames it (`postMessage(..., '*')`, `viewer.html:1523`).

**Design:**

- **`src/server/index.ts`:**
  - `server.listen(port, host)`, with `host` defaulting to `127.0.0.1`.
  - The automatic move to the next port when a port is busy keeps using the same `host`.
- **`src/cli.ts` `view`:** add the option `--host <addr>`. If the address isn't a loopback address, print a warning that the docs will be readable from the network.
- **Remove the CORS header** from `src/server/api.ts` and `src/server/watcher.ts`. The viewer is served from the same origin, so it doesn't need it.
- **Set two headers on every response:**
  - `Content-Security-Policy: frame-ancestors 'none'`, so no other site can frame the local viewer and receive its `postMessage` data. The cloud viewer serves its own copy of the page, and cloud is out of scope.
  - `X-Content-Type-Options: nosniff`.
- **Check the `Host` header.** Reject requests whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` (on the active port), or the explicit `--host` address. This blocks DNS-rebinding attacks.
- **Work offline:**
  - Add `dagre@0.8.5` (the version used today), `marked` and `dompurify` as runtime `dependencies`, with exact versions pinned in `package.json`.
  - The server serves them at `/vendor/<name>.js`, resolved with `createRequire(import.meta.url).resolve(...)`, and nothing else.
  - `viewer.html` loads `/vendor/...` instead of the CDN.
  - The Google Fonts `<link>` stays. If it fails to load, the existing CSS font fallbacks apply.
- **Sanitise Markdown:** `md = t => t ? DOMPurify.sanitize(marked.parse(t)) : ''` at `viewer.html:1087`.

**Compatibility:**

- Anyone who opened the viewer from another device must now pass `--host 0.0.0.0`. This goes in the changelog.
- This adds 3 small runtime dependencies. The trade-off is acceptable because "everything local" requires an offline viewer.

**Tests:** new `src/__tests__/server.test.ts`, which starts the server on port 0 in a temporary directory and checks that:

- the server's address is `127.0.0.1`
- there is no `Access-Control-Allow-Origin` header
- a request with `Host: evil.example` gets 403
- `/vendor/dagre.js`, `/vendor/marked.js` and `/vendor/dompurify.js` return 200
- a request for any other `/vendor/*` path gets 404

### 3. Fix the Mermaid parser (R4, S2)

**Problem:** `parseMermaid` in `src/lib/diff.ts` reads `A -->|"label"| B[...]` as an edge from `A` to `|"label"|`. Every diagram `/omm-scan` produces uses this form.

**Design:** replace the regex matching of each line with a small tokenizer for flowchart statements. In order:

1. Read a node reference: an ID followed by an optional shape (`[..]`, `(..)`, `{..}`, `((..))`, `[[..]]`, `[(..)]`, `>..]`), where text in quotes may contain bracket characters.
2. Then read zero or more pairs of an arrow and the next node reference.
3. An arrow is one of `-->`, `---`, `-.->`, `==>`, `--o`, `--x`, or `~~~`. It may have a label, written either as `|text|` right after the arrow or inline as `-- text -->`.
4. Chains like `A --> B --> C` produce two edges.
5. `&` fan-out (`A --> B & C`) is supported.

Edge identity stays `src arrow dst`, with the label excluded. This keeps `DiffResult` unchanged, so the public API doesn't change, and a change to a label alone is not reported as a removed plus an added edge.

**Out of scope:** the viewer's separate `parseFlowchart` is not changed. Sharing one parser between the browser and the CLI would need a build step for `viewer.html`. This stays in AUDIT.md as a known duplicate.

**Tests:** new `src/__tests__/parse.test.ts`:

- Fixtures copied from this repo's own `.omm/` diagrams. For example, `overall-architecture` must produce exactly 12 nodes and 17 edges.
- Chained edges, `&` fan-out, inline labels, quoted labels containing brackets, and `classDef`/`class`/`subgraph` lines are ignored.
- Diff cases:
  - an edge whose target changes is reported as removed + added
  - a change to a label alone reports no change

### 4. Whole-tree validate and references, with nested refs (R5, S2)

**Design:**

- **Walking the tree:**
  - `store.ts` gets `listAllElements(cwd?)`. It returns every element path (`persp`, `persp/child`, `persp/child/leaf`) in depth-first order.
  - It is built on `listNodes` and exported from `index.ts`.
- **Reference syntax** (approved). In `refs.ts`, `REF_PATTERN` becomes `/@([\w-]+(?:\/[\w-]+)*)/g`:
  - `@name` still means a top-level perspective, so existing diagrams are unaffected.
  - `@persp/child` refers to a nested element.
- **`refs.ts`:**
  - `getIncomingRefs` and `buildRefGraph` walk `listAllElements()` instead of only the top level.
  - `RefEntry.source_class` and `target_class` hold full paths. The shape of the type is unchanged.
- **`validate.ts`:**
  - `ValidateContext.allClasses` contains every element path, not just the top level.
  - `ref-exists` and `ref-self` compare full paths.
  - New warning rule, `ref-ancestor`: a diagram refers to one of its own ancestors. This enforces the "no child → parent references" rule the skill already states.
- **`omm validate`:**
  - With no arguments, it validates **every** element that has a diagram.
  - With a path, it validates only that element (unchanged).
  - The exit code is 1 if there is any error (unchanged).
- **`omm status`:** for each perspective, shows the number of elements and how many have a diagram or a description. This is a cheap first step toward showing documentation coverage.
- **`skills/omm-scan/SKILL.md`:** document the `@perspective/child` syntax under "Diagram Rules".

**Not in this release:**

- The viewer still treats `@a/b` as a reference to `a`, because its regex stops at `/`. Showing nested references in the viewer comes later.
- Diff for nested elements in the API and a diff view in the viewer (R8) also come later.

**Compatibility:** `omm validate` now checks more diagrams. Projects with errors in nested diagrams will now fail validation. This goes in the changelog.

**Tests:** nested references found as incoming and outgoing; `ref-exists` with a nested path; `ref-ancestor`; `validate` with no arguments reaches a nested diagram; `listAllElements` order.

### 5. One metadata format (R6, plus the stale-`children` part of R9)

**Design:**

- `writeField(className, …)` becomes a thin wrapper around `writeNodeField(className, [], …)`. This leaves one write path, and the public `writeField` export stays.
- `writeNodeField` records `git_commit` and `git_branch`, using `getGitInfo` exported from `meta.ts`. It already records `kind`, `title` and `parentPath`, so perspectives now get these too.
- `updateMeta` in `meta.ts` is no longer used and is removed. It was not part of the public API in `index.ts`.
- `deleteClass` on a nested path also removes that child from its parent's `meta.children`.
- Old `meta.yaml` files are read unchanged, because every field is optional. They are upgraded the next time the element is written. No migration step is needed.

**Out of scope:** making `meta.children` safe when several processes write at once. That belongs with the deferred parallel-scan work.

**Tests:**

- A top-level write records `kind: perspective`, `title` and the git fields.
- A nested write records the git fields.
- Deleting a nested element removes it from the parent's `children`.
- An old-format `meta.yaml` (as currently written by `updateMeta`) is still read correctly and upgraded on the next write.

## Acceptance criteria

1. Every new and existing test passes on all four CI combinations (Linux and Windows, each with Node 18 and 22). `tsc --noEmit` reports 0 errors.
2. Any element path containing `..`, an absolute path or a hidden segment is rejected by the CLI, the store and the API, and no files outside `.omm/` are touched.
3. `omm view` listens on `127.0.0.1`, sends no CORS header, rejects foreign `Host` headers, loads no scripts from a CDN, and sanitises rendered Markdown.
4. `parseMermaid` returns 12 nodes for this repo's `overall-architecture` diagram. `omm validate` reports no false `node-count` warning for it.
5. `omm validate` with no arguments covers nested diagrams. Incoming and outgoing references cover nested elements, including `@persp/child`.
6. Top-level and nested `meta.yaml` files have the same fields. Old meta files still load.
7. Changelog entries list the three behaviour changes:
   - the viewer listens on localhost only
   - `validate` checks nested diagrams
   - unsafe paths are rejected
8. None of the existing public exports in `src/index.ts` are removed or change signature. New exports are allowed.

## Validation plan

- **Automated:** the tests listed for each item, run in the CI matrix.
- **Manual smoke test:** run `/omm-scan` on this repo and on one other real repo of yours. Then:
  - `omm validate`
  - `omm view`: check that it renders, that nested groups expand, and that the sidebar's Markdown displays
  - `omm diff` after editing one diagram by hand
- **Baseline for later work:** record how long the scan took and how many elements it produced for both repos. Parallel scanning and incremental analysis will be measured against these numbers.

## Order and checkpoints

The work goes in the order 1 → 2 → 3 → 4 → 5 → 6, one commit each, using Conventional Commits. Item 6's CI workflow can be added first if you'd like the checks running during the other items.

I'll report test results after each item and stop if an acceptance criterion fails.
