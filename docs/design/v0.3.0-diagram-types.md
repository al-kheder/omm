# v0.3.0 Diagram Types — Design

- **Status:** ER, sequence and state diagrams implemented. Class diagrams proposed.
- **Roadmap:** [ROADMAP.md › v0.3.0](../ROADMAP.md#v030--new-diagram-types-in-progress)

## Goal

Let `/omm-scan` document more than component flowcharts: data models first, then sequences, states and type hierarchies. Every new type must work end to end:

- it is written by the skill
- it is checked by `omm validate`
- it is compared by `omm diff`
- it is drawn by `omm view`

## Decisions

### 1. Native renderers, not mermaid.js

The viewer draws flowcharts with its own code on top of dagre. That is what lets a diagram be nested and expanded inside another one. Bundling mermaid.js (about 2.5 MB) would:

- add a second look to the viewer
- double the page weight
- produce SVG that cannot be nested the same way

Each new type therefore gets its own small renderer, which returns the same `{ svgContent, W, H }` shape as `renderGroup`. That way it can be a perspective or a nested group anywhere in the tree.

### 2. One parser per type, shared by the CLI and the browser

Each type's parser lives in `src/lib/` (ER: `src/lib/er.ts`, sequence: `src/lib/sequence.ts`, state: `src/lib/state.ts`; shared helpers in `src/lib/diagram.ts`). It is:

- used directly by `validate.ts` and `diff.ts`
- re-exported from `src/viewer/index.ts`
- bundled by tsup as an IIFE (`dist/omm-viewer.global.js`, global `OmmViewer`), which the server serves as `/vendor/omm.js`

This avoids the problem flowcharts have today, where the CLI parser (`diff.ts`) and the viewer parser (`viewer.html`) are separate copies (see AUDIT.md §2).

### 3. Type detection

`detectDiagramType(text)` reads the first statement. YAML front matter and `%%` comments are skipped. It lives in `src/lib/diagram.ts` and returns `flowchart`, `er`, `sequence`, `state` or `unknown`. Anything that is not recognised as a new type falls through to the existing flowchart path, so current behaviour does not change.

## ER diagrams (implemented)

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/er.ts` | Entities, aliases, attributes (`type name [PK\|FK\|UK] ["comment"]`, the `*name` shorthand for PK), relationships with both cardinality markers, `--`/`..`, `direction`. Unknown lines become errors with line numbers |
| Validation | `src/lib/validate.ts` | `er-syntax` (error), `er-orphan-entity` (warning), and the existing `@ref` and size rules (counting entities). The flowchart rules are skipped for ER |
| Diff | `src/lib/diff.ts` | Nodes are entities; edges are `a ||--o{ b`. `added_attributes`/`removed_attributes` are new optional fields on `DiffResult`. Changing only a relationship label is not reported as a change |
| Viewer | `src/server/viewer.html` (`renderErGroup`) | Entity box with a header and attribute rows (key badge, name, type, comment as a tooltip). Dashed lines for non-identifying relationships. Cardinality text (`1`, `0..1`, `1..*`, `0..*`) at both ends |
| Skill | `skills/omm-scan/SKILL.md` | `data-model` perspective; "ER Diagram Rules". Entity names match child element folders |

**Not supported yet:** Mermaid's word-form relationships (`one or more`, `zero or many`), and `classDef`/`style` for ER. Both are skipped or reported, never mis-parsed.

**Tests:** `src/__tests__/er.test.ts` covers the parser, validation, diff and the `/vendor/omm.js` route. The rendering was checked in headless Chrome against a sample schema and this repo's own `data-model` perspective.

## Sequence diagrams (implemented)

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/sequence.ts` | `participant`/`actor` with `as` labels (and `create`, `destroy`, `id@{…}` accepted), messages with all ten arrows (`->`, `-->`, `->>`, `-->>`, `-x`, `--x`, `-)`, `--)`, `<<->>`, `<<-->>`) and `+`/`-` activation, `activate`/`deactivate`, notes (`left of`, `right of`, `over a,b`), blocks (`loop`, `alt`/`else`, `opt`, `par`/`and`, `critical`/`option`, `break`, `rect`), `box` groups, `autonumber`. The result is an ordered event list. Errors carry line numbers: unknown statements, messages without `:`, `end` without a block, `else`/`and`/`option` outside their block, unclosed blocks, deactivating an inactive participant |
| Validation | `src/lib/validate.ts` | `seq-syntax` (error), `seq-unused-participant` (warning), `seq-message-label` (warning for empty text), `message-count` (warning above 30), `node-count` counting participants (no too-small warning) and the `@ref` rules |
| Diff | `src/lib/diff.ts` | Nodes are participants; edges are `a ->> b: text`. The text is part of the identity because it is what was sent. A repeated identical message gets a ` (2)` suffix. Reordering messages is not reported |
| Viewer | `src/server/viewer.html` (`renderSeqGroup`) | Participant headers (stick figure for actors) with dashed lifelines; messages top to bottom, dashed replies, filled, open (async) and cross heads, self-messages as loops; activation bars; notes; labelled frames for blocks with dashed `else` separators; `rect` as a tinted band; autonumber circles. Columns are pushed apart until every message label fits. Participants link to child elements of the same id. No dagre needed |
| Skill | `skills/omm-scan/SKILL.md` | "Sequence Diagram Rules"; `request-lifecycle` suggests sequence diagrams when order matters |

**Not supported yet:** `box` groups are parsed but not drawn, `create`/`destroy` do not change where a lifeline starts or ends, and participant config (`@{ "type": "database" }`) is ignored. None of these are mis-parsed.

**Tests:** `src/__tests__/sequence.test.ts` covers the parser, arrow styles, validation and diff. The rendering was checked in headless Chrome, as a perspective and nested inside a flowchart.

## State diagrams (implemented)

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/state.ts` | `stateDiagram` and `stateDiagram-v2`: states, `state "Label" as id`, `id : description`, transitions with triggers, `[*]` start and end (scoped to the enclosing composite: ids `[*]start`, `paid/[*]end`), composite states `state x { ... }` with `parent`, `<<choice>>`/`<<fork>>`/`<<join>>`, single- and multi-line notes, `direction`, `:::class` suffixes. `--` region separators, `classDef`, `class`, `style` and `hide empty description` are accepted and ignored. Errors carry line numbers |
| Validation | `src/lib/validate.ts` | `state-syntax` (error), `state-orphan` (warning; a composite counts as connected through its children), `state-transition-label` (warning for ordinary-to-ordinary transitions without a trigger), `node-count` counting states without `[*]`, and the `@ref` rules |
| Diff | `src/lib/diff.ts` | Nodes are states (without `[*]`); edges are `a --> b: trigger`, with `[*]` shown as `[*]` |
| Viewer | `src/server/viewer.html` (`renderStateGroup`) | One dagre layout per scope, innermost first; a composite is a box with a header and its laid-out content. Transitions that cross a composite border are drawn between the outermost boxes involved. Start dot, end ring, rounded states with descriptions, choice diamond, fork/join bars, dashed notes in the next rank, trigger labels. States link to child elements of the same id |
| Skill | `skills/omm-scan/SKILL.md` | "State Diagram Rules"; `state-transitions` uses them |

**Not supported yet:** concurrent regions (`--`) are drawn as one region, the description of a composite state is not drawn, notes are placed in the next rank rather than strictly left or right, and a transition from a composite to one of its own children is not drawn. None of these are mis-parsed.

**Tests:** `src/__tests__/state.test.ts` covers the parser, validation and diff. The rendering was checked in headless Chrome, as a perspective and nested inside a flowchart.
