# v0.3.0 Diagram Types — Design

- **Status:** ER, sequence and state diagrams implemented, and flowcharts moved to a shared parser with process-flowchart support. Class diagrams proposed.
- **Roadmap:** [ROADMAP.md › v0.3.0](../ROADMAP.md#v030--new-diagram-types-in-progress)

## Goal

Let `/omm-scan` document more than component flowcharts: data models first, then sequences, states and type hierarchies. Every new type must work end to end:

- it is written by the skill
- it is checked by `omm validate`
- it is compared by `omm diff`
- it is drawn by `omm view`

## Decisions

### 1. Native renderers, not mermaid.js

The viewer draws flowcharts with its own code on top of dagre. That is what lets a diagram be nested and expanded inside another one. Bundling mermaid.js (about 2.5 MB) would:

- add a second look to the viewer
- double the page weight
- produce SVG that cannot be nested the same way

Each new type therefore gets its own small renderer, which returns the same `{ svgContent, W, H }` shape as `renderGroup`. That way it can be a perspective or a nested group anywhere in the tree.

### 2. One parser per type, shared by the CLI and the browser

Each type's parser lives in `src/lib/` (flowchart: `src/lib/flowchart.ts`, ER: `src/lib/er.ts`, sequence: `src/lib/sequence.ts`, state: `src/lib/state.ts`; shared helpers in `src/lib/diagram.ts`). It is:

- used directly by `validate.ts` and `diff.ts`
- re-exported from `src/viewer/index.ts`
- bundled by tsup as an IIFE (`dist/omm-viewer.global.js`, global `OmmViewer`), which the server serves as `/vendor/omm.js`

Flowcharts used to have two separate parsers, one in `diff.ts` and one in `viewer.html` (see AUDIT.md §2). Both now use `src/lib/flowchart.ts`; see "Process flowcharts" below.

### 3. Type detection

`detectDiagramType(text)` reads the first statement. YAML front matter and `%%` comments are skipped. It lives in `src/lib/diagram.ts` and returns `flowchart`, `er`, `sequence`, `state` or `unknown`. Anything that is not recognised as a new type falls through to the existing flowchart path, so current behaviour does not change.

## ER diagrams (implemented)

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/er.ts` | Entities, aliases, attributes (`type name [PK\|FK\|UK] ["comment"]`, the `*name` shorthand for PK), relationships with both cardinality markers, `--`/`..`, `direction`. Unknown lines become errors with line numbers |
| Validation | `src/lib/validate.ts` | `er-syntax` (error), `er-orphan-entity` (warning), and the existing `@ref` and size rules (counting entities). The flowchart rules are skipped for ER |
| Diff | `src/lib/diff.ts` | Nodes are entities; edges are `a ||--o{ b`. `added_attributes`/`removed_attributes` are new optional fields on `DiffResult`. Changing only a relationship label is not reported as a change |
| Viewer | `src/server/viewer.html` (`renderErGroup`) | Entity box with a header and attribute rows (key badge, name, type, comment as a tooltip). Dashed lines for non-identifying relationships. Cardinality text (`1`, `0..1`, `1..*`, `0..*`) at both ends |
| Skill | `skills/omm-scan/SKILL.md` | `data-model` perspective; "ER Diagram Rules". Entity names match child element folders |

**Not supported yet:** Mermaid's word-form relationships (`one or more`, `zero or many`), and `classDef`/`style` for ER. Both are skipped or reported, never mis-parsed.

**Tests:** `src/__tests__/er.test.ts` covers the parser, validation, diff and the `/vendor/omm.js` route. The rendering was checked in headless Chrome against a sample schema and this repo's own `data-model` perspective.

## Sequence diagrams (implemented)

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/sequence.ts` | `participant`/`actor` with `as` labels (and `create`, `destroy`, `id@{…}` accepted), messages with all ten arrows (`->`, `-->`, `->>`, `-->>`, `-x`, `--x`, `-)`, `--)`, `<<->>`, `<<-->>`) and `+`/`-` activation, `activate`/`deactivate`, notes (`left of`, `right of`, `over a,b`), blocks (`loop`, `alt`/`else`, `opt`, `par`/`and`, `critical`/`option`, `break`, `rect`), `box` groups, `autonumber`. The result is an ordered event list. Errors carry line numbers: unknown statements, messages without `:`, `end` without a block, `else`/`and`/`option` outside their block, unclosed blocks, deactivating an inactive participant |
| Validation | `src/lib/validate.ts` | `seq-syntax` (error), `seq-unused-participant` (warning), `seq-message-label` (warning for empty text), `message-count` (warning above 30), `node-count` counting participants (no too-small warning) and the `@ref` rules |
| Diff | `src/lib/diff.ts` | Nodes are participants; edges are `a ->> b: text`. The text is part of the identity because it is what was sent. A repeated identical message gets a ` (2)` suffix. Reordering messages is not reported |
| Viewer | `src/server/viewer.html` (`renderSeqGroup`) | Participant headers (stick figure for actors) with dashed lifelines; messages top to bottom, dashed replies, filled, open (async) and cross heads, self-messages as loops; activation bars; notes; labelled frames for blocks with dashed `else` separators; `rect` as a tinted band; autonumber circles. Columns are pushed apart until every message label fits. Participants link to child elements of the same id. No dagre needed |
| Skill | `skills/omm-scan/SKILL.md` | "Sequence Diagram Rules"; `request-lifecycle` suggests sequence diagrams when order matters |

**Not supported yet:** `box` groups are parsed but not drawn, `create`/`destroy` do not change where a lifeline starts or ends, and participant config (`@{ "type": "database" }`) is ignored. None of these are mis-parsed.

**Tests:** `src/__tests__/sequence.test.ts` covers the parser, arrow styles, validation and diff. The rendering was checked in headless Chrome, as a perspective and nested inside a flowchart.

## State diagrams (implemented)

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/state.ts` | `stateDiagram` and `stateDiagram-v2`: states, `state "Label" as id`, `id : description`, transitions with triggers, `[*]` start and end (scoped to the enclosing composite: ids `[*]start`, `paid/[*]end`), composite states `state x { ... }` with `parent`, `<<choice>>`/`<<fork>>`/`<<join>>`, single- and multi-line notes, `direction`, `:::class` suffixes. `--` region separators, `classDef`, `class`, `style` and `hide empty description` are accepted and ignored. Errors carry line numbers |
| Validation | `src/lib/validate.ts` | `state-syntax` (error), `state-orphan` (warning; a composite counts as connected through its children), `state-transition-label` (warning for ordinary-to-ordinary transitions without a trigger), `node-count` counting states without `[*]`, and the `@ref` rules |
| Diff | `src/lib/diff.ts` | Nodes are states (without `[*]`); edges are `a --> b: trigger`, with `[*]` shown as `[*]` |
| Viewer | `src/server/viewer.html` (`renderStateGroup`) | One dagre layout per scope, innermost first; a composite is a box with a header and its laid-out content. Transitions that cross a composite border are drawn between the outermost boxes involved. Start dot, end ring, rounded states with descriptions, choice diamond, fork/join bars, dashed notes in the next rank, trigger labels. States link to child elements of the same id |
| Skill | `skills/omm-scan/SKILL.md` | "State Diagram Rules"; `state-transitions` uses them |

**Not supported yet:** concurrent regions (`--`) are drawn as one region, the description of a composite state is not drawn, notes are placed in the next rank rather than strictly left or right, and a transition from a composite to one of its own children is not drawn. None of these are mis-parsed.

**Tests:** `src/__tests__/state.test.ts` covers the parser, validation and diff. The rendering was checked in headless Chrome, as a perspective and nested inside a flowchart.

## Architecture diagrams (implemented)

Mermaid's `architecture-beta` (v11) is used for the `deployment` perspective:
- **groups** are where software runs: cloud accounts, networks, hosts, clusters, containers;
- **services** are what runs there;
- **edges** are the runtime connections between them.

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/architecture.ts` | Follows Mermaid's grammar (`architecture.langium`). It reads:<br>• `group id(icon)[Title] in parent`<br>• `service id(icon)[Title] in parent`, or with `"text"` instead of an icon<br>• `junction id in parent`<br>• edges `a:R --> L:b` with optional `<`/`>`, titles `-[HTTPS]-`, and `{group}` on either end<br>• `align row\|column`, `title`, `accTitle`, `accDescr`<br>Titles may carry omm's second line (`"API\nserver/"` or `<br>`). Errors carry line numbers. As in Mermaid, an ID must be declared before it is used, groups cannot be edge ends, and `{group}` needs the service to be inside a group |
| Validation | `src/lib/validate.ts` | `arch-syntax` (error), `arch-orphan` (warning: a service without connections), `arch-edge-label` (warning: a connection without a title, except at junctions), `node-count` counting groups, services and junctions, `secret-value`, and the `@ref` rules |
| Diff | `src/lib/diff.ts` | Nodes are groups, services and junctions. Edges are `a --> b: title`; sides are layout hints and not part of the identity |
| Viewer | `src/server/viewer.html` (`renderArchGroup`) | One dagre compound layout:<br>• groups are nested dashed boxes with an icon and a label;<br>• services are boxes with an icon, title and detail line (hidden by **clean**);<br>• junctions are dots.<br>The main direction is left to right unless most edges are T/B. An edge leaves the side named in the text when that side faces the other end; `{group}` edges start or end on the group's border. Built-in icons (`server`, `database`, `disk`, `cloud`, `internet`) are drawn; other icon names get a neutral tile. In **color** mode, data stores (`database`, `disk`, storage-like icon names) and `internet` services are colored; everything else stays neutral. With **flow** on, every one-way connection gets a moving icon. Services link to child elements of the same ID |
| Skill | `skills/omm-scan/SKILL.md` | "Deployment Diagram Rules"; the `deployment` perspective uses them |

**Links to other perspectives:** a `%% @overall-architecture/server` comment links the diagram to an element, and `omm validate` checks it. Nothing is drawn, so the deployment view doesn't embed the server's internal diagram, which a node label `@…` would do.

**Not supported yet:**
- Iconify icons are not drawn; they get a neutral tile, because the viewer works offline.
- `align` is read but not applied: dagre decides the placement.
- Mermaid lays these diagrams out with fcose and follows the sides strictly, so positions differ from mermaid.live. The topology and connections are the same.

**Tests:** `src/__tests__/architecture.test.ts` covers the parser, validation, diff, comment references, flow motion and colors. It uses three fixtures: a containerized app, frontend/backend/database in network zones, and development vs production. Rendering, flow motion and export were checked in headless Chrome in both themes.

## Process flowcharts (implemented)

Flowcharts were already the default type, used for architecture diagrams. This work makes them suitable for process diagrams shown to non-technical readers, and removes the second parser.

| Part | Where | Notes |
|---|---|---|
| Parser | `src/lib/flowchart.ts` | One parser for `diff`, `validate` and the viewer. Classic shapes (`[ ]`, `( )`, `([ ])`, `[[ ]]`, `[( )]`, `(( ))`, `((( )))`, `{ }`, `{{ }}`, `[/ /]`, `[\ \]`, `[/ \]`, `[\ /]`, `>  ]`) and `id@{ shape: …, label: … }` for the common flowchart shape names (`doc`, `start`, `stop`, `subproc`, `lean-r` …; unknown names become rectangles). `-->|label|` and `-- label -->` edges, chains, `&`, line styles (`-.->`, `==>`, `~~~`), arrow ends (`--o`, `--x`, `<-->`), lengths, `:::class`, `class`, subgraphs with labels, nesting and `direction`. A literal `\n` in a label starts the `detail` line that `/omm-scan` uses for file paths; `<br>` is an ordinary line break. Errors carry line numbers |
| Validation | `src/lib/validate.ts` | `graph-declaration` accepts `flowchart` without a direction. New `flowchart-syntax` (error). A flowchart with a start/end node is a *process flowchart*: `edge-label` then applies only to edges leaving a decision, and `decision-branches` warns about a decision with fewer than two ways out. Architecture flowcharts keep the old `edge-label` rule, now per edge, with `-- text -->` counted as a label and connectors exempt |
| Diff | `src/lib/diff.ts` | Unchanged output (`src arrow dst`, legacy `@id` nodes keep the `@`). Headers of unsupported types (`pie`, `gantt` …) are no longer read as a node |
| Viewer | `src/server/viewer.html` (`renderGroup`) | Shape outlines for every symbol, wrapped labels, dotted/thick edges and circle/cross ends, edge labels with reserved space, edges clipped to diamond and circle outlines. Subgraphs are dagre compound clusters drawn as dashed, labelled lanes; an edge to a subgraph goes to its first node |
| Viewer toolbar | `src/server/viewer.html` | **clean** hides `detail` lines; **svg**/**png** download the selected perspective (or everything), rendered again at 1:1 in the current theme without click handlers or overview labels |
| Skill | `skills/omm-scan/SKILL.md` | "Process Flowchart Rules" and the `business-processes` perspective; `/omm-view` mentions the toolbar |

**Not supported yet:**

- Lanes are boxes around their nodes (as in Mermaid), not full-width parallel bands.
- An edge to a subgraph is drawn to its first node rather than to the box.
- The viewer may still turn a very wide `LR` diagram into `TB` for readability.
- Exported files use the reader's system font if Inter is not installed.
- Edge IDs (`e1@-->`) and edge animation are not read. Mermaid shape names outside the flowchart set are drawn as rectangles.

**Tests:** `src/__tests__/flowchart.test.ts` covers the parser (every symbol, label forms, line styles, chains, loops, subgraphs, errors), validation and diff. The existing `parse.test.ts` and `validate.test.ts` pass unchanged. Every flowchart in this repo's `.omm/` parses to the same nodes, labels, classes, references and edges as before (edge labels no longer keep their quotes). Rendering, lanes, clean view and export were checked in headless Chrome.

## Color mode (implemented)

A viewer-only display setting: **mono** (the original look, default) or **color**. It never changes `.mmd` files.

- **One palette:** `src/lib/palette.ts`, bundled into the viewer. `nodeColors(mode, theme, role, cls)` returns fill, border and text; every renderer asks it for colors through `nodeStyle(node, role)`. In monochrome it returns the original values, so monochrome output is unchanged (compared in headless Chrome for all four types and both themes).
- **Roles, not random colors.** Color is used only where meaning is known:

| Diagram | Colored by | Roles |
|---|---|---|
| Flowchart | Shape (`flowNodeRole`) | start/end, decision, input/output, document, subprocess, data, connector; plain boxes are *steps* only in process flowcharts (those with a start/end node) |
| Flowchart | Category class (wins over shape) | `entry`, `store`, `external`, `concern`, `error`, `success` |
| ER | Notation | entity header |
| Sequence | Notation | participant, activation bar, note |
| State | Notation | state, choice, note, composite state |

  Unclassified architecture nodes, edges, lanes, ER key badges, sequence `rect` bands and UML start/end markers keep their existing look. There is no universal color standard for these notations; the hues follow common flowchart practice and the category colors `/omm-scan` already uses.
- **Accessibility:** `palette.test.ts` checks every role in both themes: text on its fill at least 4.5:1 (WCAG 1.4.3), outline against every background a node can sit on at least 3:1 (WCAG 1.4.11). Shapes and labels carry the meaning; color only reinforces it.
- **Switch:** a `mono | color` segmented control (`role="group"`, `aria-pressed`, visible keyboard focus). The choice is stored in `localStorage` (`omm-diagram-colors`), like the theme; it is per browser, not synced. Switching rebuilds the canvas (about 25 ms for 70 nodes) and keeps zoom, pan and selection.

**Not covered:** custom `classDef`/`style` colors other than the six category classes are still ignored; class diagrams are not supported yet; the toolbar is hidden on phones (a stored mode still applies).

## Edges and flow motion (implemented)

**Readable edges.** Edge colors come from `edgeColors(theme)` in `palette.ts` and are tested like node colors: lines at least 3:1 against every background (the light theme moved from `#94a3b8` to `#64748b`), label text at least 4.5:1. All renderers share one arrowhead marker (10×8). Labels are drawn after every line. In the compact fan-out grid, edges end on the child's border, and an edge that would cross another child runs along the gap left of its column. Unlabelled parallel edges are spread apart. There is no new layout engine: dagre still routes everything.

**Flow motion.** This is an optional viewer setting (**flow**, stored as `omm-flow`). A small file icon travels along the edges that stand for movement. `src/lib/flow-motion.ts` decides which edges, from the diagram text only:

| Diagram | Moves |
|---|---|
| Process flowchart (has a start/end node) | every one-way arrow; `e1@{ animate: false }` opts one out |
| Other flowcharts | only edges marked `e1@{ animate: true }` (or `animation: fast/slow`) — an architecture edge may be a dependency such as "implements" |
| Sequence | every message, one at a time in diagram order |
| State, ER | nothing — a transition or relationship is not data in transit |

Two-way (`<-->`), undirected (`---`) and invisible (`~~~`) edges never move unless explicitly marked. Edge IDs use Mermaid's own syntax (`a e1@--> b`), so the same files render in Mermaid.

- **How:** each moving edge's `<path>` gets an `id`, and the icon uses `<animateMotion><mpath href>` on it. It follows the exact rendered curve from source to target and scales with zoom. It uses no JavaScript timers.
  - The icon is drawn above lines but below labels and elements.
  - It starts at the source's border and stops 18 px before the arrowhead.
  - It is hidden between trips.
  - Flowchart edges loop with staggered starts.
  - A sequence diagram runs as one cycle, so message *n+1* moves after message *n*.
- **Limits:**
  - At most 60 icons per canvas; the remaining edges stay static, and their arrowheads still show the direction.
  - Icons are hidden in the zoomed-out overview and in collapsed groups.
  - Animations pause while the tab is hidden.
  - With flow off, nothing is added to the SVG.
- **Accessibility:** off by default, and always off when `prefers-reduced-motion: reduce` is set (the button is then disabled and says why). Direction is still shown by arrowheads. The icon fill has at least 3:1 contrast against the background, and its outline at least 3:1 against the line.
- **Export:** SVG/PNG downloads never contain icons.
- **Verified in headless Chrome:**
  - All 47 icons in the test project stayed within 0.5 px of their path while moving.
  - Every icon moved away from its source.
  - Icons were hidden between trips and stopped before the arrowhead.
  - A rebuild left no extra icons.
  - Frames stayed at 16.7 ms (p95).
